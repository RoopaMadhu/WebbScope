# WebbScope — proof of concept

A standalone app (own Python inside, nothing to install) that opens a **project folder** and gives the same browser, windows and
analyses as the original, separate browser app this one grew out of (not part of this repository). Its analysis code and UI files were *copied* here
(`webbscope/engine/*.py` and `webbscope/web/app.js`, `style.css` are byte-identical copies; `index.html` differs by four lines: bundled deck.gl
instead of the CDN, an "open another project…" link, and the page title / header now reading WebbScope).

## Open it
- Double-click `dist/WebbScope.app` (first time: right-click → Open; it is unsigned), then **Browse…** → your project folder.
- or `dist/WebbScope.app/Contents/MacOS/WebbScope /path/to/project` (add `--browser` to use the default web browser).
- dev: `.venv/bin/python run_app.py /path/to/project`;  rebuild the app: `./build_app.sh` (must run on the target OS).

## Project folder format
| file | needed for |
|---|---|
| `project.json` | **required**: name, `roles` (which column is cell id / x / y / sample / cell type / state / region levels / lib size), `norm_scale` |
| `matrix.mtx.gz`, `features.tsv.gz`, `barcodes.tsv.gz` | **required**: raw integer counts, genes x cells (10x layout; cells x genes is detected) |
| `cells.parquet` | **required**: one row per cell (cell id, x, y, sample + any metadata; every sample must be one block or is reordered) |
| `cell_boundaries.parquet` | **required**: Xenium long format `cell_id, vertex_x, vertex_y` |
| `regions.geojson` | Regions, Region neighbourhoods, Glomeruli, region filters. Pathologist outlines **already in cell coordinates and assigned to samples**: each feature has `sample`, `annotation_name`, `region_id`, `negative_roa`, `line_color_hex`, `tissue_id` |
| `embeddings.parquet` | Embeddings: `cell_id, umap_harmony_1/2, pca_harmony_1..k` |
| `gloms/gloms.json` + `gloms.npz` | ROI heterogeneity: ROI table, cell ids per ROI, ROI-level expression / PCA / UMAP (`pca_harmony` optional; per-ROI type/state counts are recomputed on import). Can instead be made at open time from a region_heterogeneity `.rds` / `.qs2` (`webbscope/roi_object.py`, `webbscope/rds.py`; see README) |
| `signatures.json` | Signatures, violins |
| `scffpe_composition.json` | Xenium vs scFFPE |
| `transcript_tissue.parquet` (batch import, optional box) | Per run: `row`, `transcript_id` (if the raw file has it), `tissue`, `sample`, `assignment` for each raw transcript of a tissue; to join to the raw `transcripts.parquet`. Not read by the viewer. Transcripts are matched to cells by the raw `cell_id` compared as text, so runs with integer cell ids (older Xenium output) work too; an import stops with an error if fewer than 1% of the transcripts carry a cell id that is in the cell table. Checked on synthetic runs only (including one with integer ids) (1 and 2 tissues, 203,000 transcripts): row/id join, tissue of every assigned row and of the nearest-cell rows verified against the raw file; ~0.95 MB |
| `transcripts/` | Transcript overlay (Left panel → Transcripts): `tx_x.npy`, `tx_y.npy` (float32, µm), `tx_ptr.npy`, `index.json`; sorted by tissue then gene; read in place (memory-mapped) |
| `he_slide.json` (+ `he/<key>/` tiles, `he_slide_annotations.geojson`) | **H&E slide window** (toolbar → *H&E slide*): a slide scan (Zeiss `.czi`, or an OME-TIFF `.ome.tif` / `.ome.tiff`) tiled per scanned section, with ImageScope annotations; **not registered** to the Xenium coordinates |
| `if.json` | **IF (morphology) image**: `images` {key: file (absolute, plus path relative to the project), w, h, px, tsize, nz, channels [{name, ifd, lo, hi}]} and `samples` {sample: key}. The image is read in place; tiles are rendered on request by `if_image.py` (`/api/if`). Checked on one real run (see README, IF images) |
| `he/`, `he_gloms/` | H&E views: **pre-tiled** pyramids and per-glom crops (`index.json` + tiles); read in place. `he/` can be made from registered OME-TIFFs with `python -m webbscope.he_registered` (checked on one image: same 5,685 tiles and same `he/index.json` entry as the earlier pyramid, mean tile difference 0.6–2.2 of 255); `he_gloms/` is still prepared elsewhere |

The import writes a cache to `~/.webbscope/cache` (override: `WEBBSCOPE_CACHE`), never into the project folder; it is redone
automatically when an input changes, including when the sample / donor columns chosen when opening change.

## Import a Xenium output bundle
From the open-project page: **Import a Xenium output bundle…** (`/xenium`). Input is the `.tar.gz` or `.zip` of a Xenium output, its extracted folder, or the files separately
(count matrix folder, `cells.parquet` / `cells.csv.gz`, `cell_boundaries.parquet` / `.csv.gz`, optional 10x `clusters.csv`, UMAP and PCA `projection.csv`).
- **Only these are read**: `cell_feature_matrix/*`, cells, cell boundaries, `experiment.xenium` and the three 10x analysis files. Images, transcripts, zarr copies, nucleus boundaries and
  differential expression are never extracted. From a tarball the needed members go to `~/.webbscope/staging/` (reused next time) and reading stops once all were seen (77 % of the 8 GB
  test archive, a few minutes).
- **Genes**: only rows typed "Gene Expression" are kept (the 9,377 rows of the test run are 5,101 genes + deprecated / negative-control / unassigned codewords and control probes).
- **Tissues**: one slide can hold several sections. They are found by cell density (50 µm grid, pieces closer than the *merge distance* are one tissue, small pieces are off by default) and
  shown on a preview where you can change the distance and the minimum size, rename (the same name merges pieces), switch pieces off, or draw a rectangle or a free-hand outline (hold the mouse button and trace) to split a piece, join pieces or cut an area out
  (a drawn shape also claims the stray isolated cells inside it; self-crossing outlines are repaired, a tiny scribble is ignored). Each tissue becomes a project *sample*. Cells with fewer panel-gene transcripts than the minimum (default 1; the 10x analysis also leaves out empty cells) are left out.
- **Cell labels**: the 10x graph clusters are the stand-in cell type and state ("Cluster 7"). Or give an annotation file (csv / tsv / parquet with a cell-id column): pick its id, cell type and (optional) cell state columns;
  unmatched cells become "unlabelled". The 10x cluster stays as column `cluster_10x`.
- **Embeddings**: the 10x UMAP and PCs fill the embedding slots. They are *not* batch-corrected, so the project says so (`embedding_label`) and the Embeddings window is labelled "10x…" instead of "Harmony".
- **Output**: a normal project folder (default `~/.webbscope/projects/<run>`), opened right away. An existing folder is only replaced if it is an earlier import of this kind; the input is never modified.
- **Transcripts** (tick *Include the transcripts* before Read; from a tarball this extracts `transcripts.parquet`, ~300 MB, in the same pass): decoded transcripts with quality >= 20 and panel genes only, stored per tissue and gene (the 23.0 M-row test file gives 20.1 M stored transcripts, 161 MB, about 10 s). A transcript belongs to the tissue of the cell it was assigned to; unassigned panel-gene ones go to the tissue of the nearest kept cell at any distance (counted separately as `unassigned_far`; older imports dropped those more than 25 µm away), and those of cells you left out are dropped. In the viewer: *Transcripts* in the left panel, type up to 8 genes; only the part in view is loaded (debounced on pan / zoom) and, above the point limit (50k / 200k / 500k), thinned evenly per gene, with the counts shown. Not stored: z, quality, nucleus distance, cell id; `transcripts.csv.gz` is not read.
- **Many runs at once** (`/xenium-batch`, link on the open-project page): give a folder that holds many Xenium output folders (or many `.tar.gz` / `.zip` bundles, not a mix). Each run is converted in turn with automatic tissue detection and default settings into `<out>/<run>/` (a failing run is logged and skipped), then all tissues are merged into `<out>/_merged`, which opens. In the merged project: sample `<run>_tissue_N`; `disease_subtype` (and `disease_type`) = the run folder, so the viewer's by-subtype grouping (gallery, z-scoring, violins) groups by run; cell type / state `<run>_tissue_N: Cluster K` (10x clusters are not comparable between runs); genes = those present in every run (the dropped ones are logged); no embeddings; cells start grey (`default_grey` in `project.json`). Transcripts are optional on the batch page (ticked by default): each run's `transcripts.parquet` is stored per run as in the single import, and the merged project's `transcripts/` concatenates them per `<run>_tissue_N` (a run without the file gets no points); this adds a few hundred MB per run and, from a `.tar.gz`, reads each archive further. H&E scans can be added in the batch import from a folder of `.czi` files (see the README: *H&E scans in a batch import*): each run is matched to a scan by the numbers in the file names, the tiles are written once per scan to `<out>/_he/<scan>/`, and the merged project's `he_slide.json` (`{multi, scans, runs}`) lists them. Checked on synthetic runs and synthetic `.czi` files (3 of 4 runs matched, one scan shared by two runs, tiles reused on a second run); not on real scans at scale. Checked on synthetic transcripts (2 runs with points, 1 without: per-gene counts identical to the raw files); the branch for runs with different gene lists is untested. The merged matrix is stored as `matrix.npz` (the importer accepts it instead of `matrix.mtx.gz`) because a text matrix of many runs is too slow. Checked on synthetic runs cut from the sample project (3 folders, 2 tar.gz, one broken archive): per-tissue counts identical to the source, labels as above; not yet on real multi-run data or at scale (the log reports peak memory). A folder of project folders this app already wrote (e.g. the per-run folders of an earlier batch import, next to its `_merged`) is also accepted: they are merged without converting again (the old `_merged` folder is skipped and rewritten); tick the transcripts box to link their stored transcripts.
- **H&E slide** (optional; two fields under *H&E slide scan* on the import page, or `python -m webbscope.he_slide scan.czi --annotations scan.annotations --project PROJECT_FOLDER` for an existing project): the CZI is read with `pylibCZIrw` (8-bit RGB brightfield only) and every scanned section (scene) becomes a pyramid of 512 px JPEG tiles in the viewer's `he/` format (level 0 = full resolution; the 0.17 µm/px, 122,340 x 64,563 px test scan gives 21,121 tiles, 512 MB, about 40 s). Annotations (`.annotations`, ImageScope XML; polygons, with `NegativeROA` flagged) become `he_slide_annotations.geojson` in µm of the slide frame (origin = top-left of the scan's bounding box, y down, the frame ImageScope uses). Unscanned parts of the mosaic are white at every level. The viewer's **H&E slide** window (floating, draggable) shows the sections with a section list (click to zoom), the annotation names with polygon counts (click to hide), an annotations switch and an opacity slider. It is independent of the cell viewer until the H&E is registered to the Xenium coordinates, which is not built yet. Needs `pillow` and `pylibCZIrw` in the build environment.
- **Grey cells** (left panel, Display): draws all cells in one grey, fill and outline, over whatever colouring is chosen, so overlays such as transcripts stand out; filters still apply (cells filtered out stay dimmed).
- **Not there yet**: H&E / IMC, pathologist regions, signatures. Without `signatures.json` the Signatures window says so, Violins start from the first gene, and the ROI heterogeneity button is hidden when there is no glom object (so `app.js` now differs from the browser copy in these few lines).
- Not supported: `cell_feature_matrix.h5` and the zarr files (use the `matrix.mtx.gz` triplet).

## What was checked
`xenium_app_poc` vs the original browser on the same tissue: 45 / 45 comparisons identical (coordinates, boundaries, labels, region
membership, outlines, all 4,131 genes x 2 layers, smoothing, neighbours (radius / kNN / Delaunay), violins, signature statistics,
scFFPE comparison, glom table and colouring, UMAP / PCA, H&E bytes) — also against the bundled app. Run with the browser server on 8766
and the app on 8791. Every toolbar window opens without script errors. The ROI heterogeneity window (formerly Glom heterogeneity) shows the Harmony-corrected PCA, the uncorrected PCA and the UMAP side by side (ported from the browser). The gene / signature filter (Filters → Gene / signature positive) is ported and passes the same 20 server checks (counts vs numpy) and 24 browser checks (real typing, AND, negative, smoothing, windows) as in the browser. Transcript import checked against the raw parquet (6 genes x 5 tissues: every x, y and count identical; total and per-tissue totals equal; bounding-box and thinning checks) and in the viewer (12 checks). Xenium import checked on one run (8 GB archive, 118,941 cells, 5 tissues): counts of 7 genes in all tissues, positions, cluster labels, UMAP and boundaries equal the raw files; tarball and folder and separate-file inputs give identical projects; error paths (missing / wrong files, foreign output folder) refuse safely. Not exercised: z-scoring pooled over several tissues
(`scope` = all / subtype / type) and multi-tissue projects, large datasets, the native window's file downloads.

## Known limits
- Still kidney-specific in code: `engine/signature_defs.py` (curated signatures) and the disease-subtype order in `engine/sigstats.py`.
- The app does not make the optional inputs: tissue-to-sample matching of outlines, the per-glom H&E crops are prepared elsewhere; the R region_heterogeneity object is read at open time (README). Checked on one object (`gloms_for_claude_kidney_edp_1_2_no_tubules.qs2`, 266 ROIs) opened with the one-tissue sample project: 16 ROIs linked to cells, the same ROIs, order and cell membership as the sample project's own glom files; the object's embeddings and expression differ from those files (another build), so they were not compared.
- Unsigned (Gatekeeper warning). Linux build: see the section above (untested).

## Linux / HPC (server-only build)
There is no native window on a cluster: on Linux the app starts **headless** (`--window` tries the native one), and you view it in a browser on your own computer through an SSH tunnel.
Target checked: x86_64, glibc 2.34, RHEL 9. PyInstaller cannot cross-compile, so the Linux build is made on the cluster.

1. On the Mac: `./pack_source.sh` (source, ~700 KB); `scp` it to the cluster and unpack.
2. On the cluster (compute node or interactive job, internet / pip mirror needed once): `module load python` (3.10+ needed), then `bash build_linux.sh` → `dist/WebbScope-linux-x86_64.tar.gz`
   (a `dist/WebbScope/` folder you can also run in place). Build on the oldest machine you will run on (the binary needs glibc >= the build machine's).
3. Run it in a job, e.g. `srun --pty -c 8 --mem 32G bash`, then `WEBBSCOPE_CACHE=$SCRATCH/webbscope_cache dist/WebbScope/WebbScope --port 8765 /path/to/project`.
   It prints the exact `ssh -L … -J login-node compute-node` command; run that on your computer and open `http://localhost:8765`.
4. There is no Browse… dialog on Linux: type the project path (the pages already allow this). The cache goes to `~/.webbscope` unless `WEBBSCOPE_CACHE` is set; on a cluster point it at scratch / project storage.
- No pip on the cluster? Run from source instead: `python -m venv v && v/bin/pip install -r requirements-linux.txt && v/bin/python run_app.py PROJECT`.
- Not tested on Linux yet (no Linux machine here); expect to iterate on the first run.

## Resource estimates (batch import and viewer)
Measured on a Mac (one core used; warm local SSD) with a **synthetic** run of the size of the 8 GB test archive: 121,380 cells, 4,131 genes, 23.7 M non-zero counts, 23 M transcripts (the sample tissue tiled 14 times), as an extracted folder. Real data and cluster storage were **not** measured; the figures beyond 6 runs are linear extrapolations.

| step | measured | extrapolated |
|---|---|---|
| convert one run (read, tissues, write project, 18.4 M transcripts kept, signatures) | 17 s, peak 3.9 GB | |
| convert N runs + merge (peak RAM grows ~0.5 GB per run: the converted counts are held for the merge) | N = 6 (727k cells): 106 s, peak 7.1 GB; merge alone 4 s | N = 20: ~6 min, ~13 GB; N = 50: ~15 min, ~29 GB |
| disk per run | run project 232 MB (141 MB of it transcripts) + merged project ~200 MB + viewer cache ~200 MB, so ~0.6 GB | N = 50: ~30 GB |
| first open in the viewer (builds the cache) | 727k cells: 8 s, peak 1.7 GB; re-open (cache current) 1 s | 12 M cells: ~2 min, ~28 GB |
| viewer at rest / browsing | ~0.6 GB resident after opening 727k cells; tissue load, gene colouring and smoothing: milliseconds (first smoothing of a tissue 0.03 s); z-score pooled over all 84 tissues: 1.8 s, +0.3 GB | |
| transcripts | not loaded at open (memory-mapped, one gene of one tissue is one slice; the merged project reads each run's own folder) | |

- The conversion is single-threaded (user time ~ elapsed time): more cores do not help, memory does. A job for N runs of ~120k cells: about 4 + 0.5 x N GB plus margin.
- From **.tar.gz** bundles the conversion time is dominated by reading the archive, which is not in the table: the earlier single-run test on the real 8 GB archive needed a few minutes per run (README above), so N archives take roughly N times that, and with transcripts each archive is read further. Staging copies go to `<WEBBSCOPE_CACHE>/../staging`.
- On a shared / network filesystem the many file writes can be slower than here; time one real run first and multiply.
- Reproduce: `mkbig.py`-style synthetic data was used (not shipped); the batch log prints elapsed time and peak memory after every run.

## Profiling
Always on, nothing to enable. The **Profile** button in the viewer's toolbar (or `/profile`, `/api/profile`) shows, for the last project opened: the named steps (prepare / import into the cache / building the engine / transcripts index) with seconds and peak memory; every log line with its time, the time since the previous line and memory (resident memory is read on Linux only; elsewhere only the peak); and, for the requests since then, one row per API endpoint (calls, total / mean / max / last ms, MB sent; tissues are grouped under one endpoint). **Reset request timings** starts a fresh measurement, e.g. right before opening one window; **Copy as text** gives a paste-able report. Browser-side drawing time is not included.

## QC report per tissue
Toolbar → **QC report** (or `/qc/<tissue>`) opens a one-page report for the current tissue: a self-contained HTML page (inline SVG charts, embedded PNG maps, no extra files) that prints to one A4 page; use the browser's *Print / save as PDF*. **Export all tissues…** on the report page (or `POST /api/qc/export {folder, samples?}`) writes `<tissue>.html` for every tissue plus `qc_summary.csv` (one row per tissue with the metrics and flags) to a folder on the machine running WebbScope. About 0.2-0.3 s per report.

**All-tissue summary** (`/qc-summary`, button in the QC report, and `qc_summary.html` written by *Export all tissues…* next to `qc_summary.csv`): one strip plot per metric with every tissue as a dot (log axis when the values span more than about 1.5 decades), a dashed line at the 1st percentile on the bad side, a small table of the tissues beyond the line, and a plain-language description of the metric. Names are shortened by removing the beginning shared by all tissue names (shown at the top of the page; hover for the full name).
Contents (all computed from what the project stores, nothing from the original Xenium output): header (project, run, slide / panel / software when known); cards (cells, approximate area, cells per mm², median transcripts and genes per cell, high-quality transcripts in the tissue when transcripts were imported, else the share of low-count cells); map of cells coloured by transcripts per cell; histograms of transcripts per cell, genes per cell and cell area; segmentation methods and share of cells with a nucleus; transcripts vs cell area; genes ranked by counts; detection rate vs mean expression per gene; transcript density map (with transcripts) or the largest 10x clusters (without); this tissue against all other tissues of the project (strip plot, percentile, flag = robust z-score beyond ±3, only with at least 6 tissues; a comparison inside the project, not a pass / fail against a 10x specification); cells without a boundary.
**Recorded at import (projects imported with this version; older projects say "not recorded" and need a re-import):** the counts of the non-gene features per cell (negative control probes / codewords, unassigned and deprecated codewords) are stored as cell columns `nc_probe_counts`, `nc_codeword_counts`, `unassigned_codeword_counts`, `deprecated_codeword_counts` (so they can also be used as a numeric colouring) with the number of control features per type in `project.json` (`controls`, per run in merged projects); the report shows them per type and as a **background level** = negative-control counts per control feature as a % of the mean counts per gene. With transcripts, `transcripts/index.json` (per run) gets a `qc` block: per tissue the quality-value histogram (QV 0-40) of the panel-gene transcripts assigned to a cell of the tissue (any quality), and the Q20-or-better transcripts assigned to a cell versus unassigned but within 25 µm of the tissue; plus the run-wide share assigned to any cell. The report shows the QV histogram (share at Q20 or better) and the assigned share (tissue level and run level). The tissue-level assigned share only counts unassigned transcripts within 25 µm of the tissue, so it reads higher than a slide-wide figure; the run-level one is slide-wide. These three numbers also enter the cross-tissue flags and `qc_summary.csv`.
Checked on synthetic runs with 70 control features and 10% unassigned transcripts: control counts per cell, the QV histogram and the assigned counts identical to a recomputation from the raw files; report prints on one A4 page (the page scales itself to fit when printed). Panels that need a column the project lacks (cell area, nucleus area, segmentation method) say so. Checked on the sample project (single tissue) and on a synthetic 14-tissue project with transcripts (screenshots, export of all 14, error paths); not on real multi-run data.

**Gallery export.** With the Gallery open, *Save PNG → Everything* draws every tile again at high resolution onto numbered pages (5000 × 3500 px, 5 tiles per row, section headers kept) and downloads them as one `.zip` of PNG files (`<name>_p01.png`, `_p02.png`, …). The H&E underlay is not included in this export; *What I see now* is unchanged.

**Reusing an earlier merge.** On the batch page, if `<folder>/_merged` (or `<output>/_merged`) already exists from an earlier batch import, a box offers *Open it (no merging)*; it says how many runs / tissues / cells it holds and whether it lists the same runs as the ticked ones. The same project can always be opened directly by its path.

**Colour bars** carry five labelled values (not just the two ends); a log-scaled colouring is labelled at equal steps in log space.

## Publication figure

**Figure…** (next to Save PNG) makes a journal-style figure of the main view: Arial/Helvetica text at 5–7 pt (default 7 pt, legend 1 pt smaller), an 8 pt bold lowercase panel letter, widths of 89 mm (1 column), 120 / 136 mm (1.5 columns) or 183 mm (2 columns), a maximum height (default 170 mm, legend included), a scale bar, and the colour legend or bar with five labelled values. Choose 300 or 600 dpi and either the view as it is on screen or the whole tissue; the dialog shows a live preview and the exact size in mm and pixels. Cell outlines (0.25 pt) are drawn when cells are large enough to see; otherwise cells are filled squares.

- **PNG** records its physical size (pixels per metre) in the file.
- **PDF** has live Helvetica text and a vector scale bar and colour bar; the cells are one image at the chosen dpi. The standard Helvetica font is referenced, not embedded.
- The H&E slide is not part of the figure.
- The sizes follow Nature's figure guide (column widths, 5–7 pt text, 170 mm maximum height). The 8 pt bold panel letter and the dpi values come from third-party summaries; check them against the journal's current instructions.

## Slide view

**Slide** (toolbar, next to Gallery) shows every tissue of one slide at its true position, each in a labelled box (short name such as `tissue_2`, plus its cell count). The slide is the run: tissues of an imported run share one coordinate frame, so the selector lists one entry per run (for a merged project, one per run folder). Cells follow the current Colour by, filters and Grey cells; the box of the tissue you are viewing is blue, and clicking a box opens that tissue. Save PNG saves the slide picture. The selector's first entry, **All slides**, shows every slide on one scrolling page (1, 2 or 3 per row) on a common scale (the same µm per pixel everywhere) with one colour scale over all tissues, so slides can be compared directly; each slide is drawn when it scrolls into view. For a gene, signature or numeric colouring the shared scale needs every tissue's values first, so the first draw loads them all (progress is shown). Save PNG in this view writes `slides.zip` with one picture per slide. Only the cells kept at import appear: pieces switched off in the tissue preview, or below the minimum transcript count, are not in the project.

## Negative-control density (QC report)

Next to the transcript density map, the per-tissue QC report has a map of the negative controls, with the same 20 µm bins, coloured by the number of negative-control transcripts per bin (1, 2, 3 … 8+, linear; grey = tissue bin with none), and the density per mm² in the note. Negative controls are the transcripts whose `codeword_category` is `genomic_control_probe`, `deprecated_codeword`, `negative_control_probe`, `negative_control_codeword` or `unassigned_codeword` (QV ≥ 20, assigned to a cell of the tissue or unassigned within 25 µm of one); `predesigned_gene` and `custom_gene` are the positive (gene) probes. The note gives the count per class. A transcript file without that column falls back to the feature-name prefixes (`GenomicControlProbe`, `DeprecatedCodeword`, `NegControlProbe`, `NegControlCodeword`, `UnassignedCodeword`). The all-tissue summary gets a matching strip plot ("neg. controls per mm²", high = bad). The positions are recorded at import, so runs imported before this version show a note and need to be imported again.
